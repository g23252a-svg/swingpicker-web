# v71 — 시점별 유니버스 복원 (생존편향 제거의 1단계)

> 2026-08-27 · 과제 #15. 코드 변경 아님, **신규 모듈만** 추가.
> `PRODUCTION_BUY` / 사이징 / `stop_logic` / 야간 배치 경로 전부 무변경.

## 왜

`docs/SELECTION_SEARCH_20260827.md`에서 확인된 것: `data/ohlcv_cache_*.parquet`는
593종목이고 **중도 소멸 흔적이 0건**이다. 편입 게이트(`top_n=600`,
`min_turnover_eok=50`, `min_mcap_eok=1000`)를 완화하는 게 옳은지 검정하려면
사라진 종목이 있는 유니버스가 필요하다. 저유동·소형 구간이야말로 생존편향이
가장 심한 구간이라, 지금 데이터로 "저유동이 낫다"는 결론을 내면 그건 죽은
종목을 빼고 센 결과다.

## 무엇을 만들었나

### `services/universe_history.py`
`data/krx_codes_YYYYMMDD.csv` 130개 스냅샷에서 시점별 상장 여부를 복원한다.

```
[v71] 유니버스 2,841종목 (소멸 확인 46 · 미확인 2) · OHLCV 보유 574 / 결손 2,267 ·
      소멸종목 시세 보유 0/46 · 스냅샷 130개 중 붕괴 14개 제외
```

**붕괴 스냅샷 방어.** 130개 중 14개가 수집 실패로 잘려 있다(20260227 107종목,
20260813 379종목 등). 그대로 쓰면 하루에 2,700종목이 상장폐지된 것으로 잡힌다 —
v65에서 잡은 팬텀 세션과 같은 부류다.

기준 크기는 **반복 절사 중위**로 잡는다. 롤링 중위를 먼저 써봤으나
2026-02-27~03-06 **6일 연속** 장애 구간에서 롤링 중위 자체가 오염되어
붕괴를 못 잡았다(전 종목 `gap_max`가 6으로 찍히는 것으로 발각). 전역 중위에서
시작해 기준 미만을 떨어내고 다시 중위를 잡기를 반복하면 정상 모집단으로 수렴한다.
버리는 비율이 30%를 넘으면 경고를 남긴다.

**소멸 판정.** '유효 스냅샷에 있다가 이후 유효 스냅샷 3개 연속 부재'만 소멸로
인정한다. 관측 구간 끝이라 확인 창이 모자라면 `UNCONFIRMED`로 남기고 소멸로
세지 않는다 — 모르는 것을 안다고 말하지 않기 위해서다(현재 2종목).

### `scripts/backfill_universe_ohlcv.py`
결손 2,267종목의 일봉을 `data/universe_ohlcv/<code>.parquet`로 채우는 독립 스크립트.

- **야간 배치에 물리지 않는다.** 2,267종목을 매일 받으면 배치 시간이 폭증하고
  실패 시 추천 산출 자체가 위험해진다. 일회성 백필 + 가끔 증분이지 매일 할 일이 아니다.
  `pipeline_finalize`가 이 모듈을 부르지 않는다는 것을 테스트로 고정했다.
- `_manifest.json`에 종목별 상태(ok/empty/error)를 남겨 **재개 가능**하다.
  실패만 다시 하려면 `--retry-failed`.
- 등락률 단위는 **출처가 선언**한다(FDR=비율, pykrx=%). 값 크기로 추측하던 첫 판본은
  "매일 +1.23%씩 오른 종목"을 비율로 오인해 123%로 만들었다. 기본값은 아예 출처의
  등락률을 안 쓰고 종가에서 다시 계산한다.

```
python scripts/backfill_universe_ohlcv.py --status
python scripts/backfill_universe_ohlcv.py --start 2025-02-01 --limit 200
```

## 곁가지로 잡은 것 — 테스트가 저장소의 `data/`를 더럽힌다

작업 중 `git status`에 `data/ohlcv_union_hl.parquet`이 수정된 채 남았다.
내용은 HEAD와 **완전히 동일**했다(`equals()` True) — 데이터는 그대로인데
파일 바이트만 다시 쓰인 것이다.

범인은 v65·v69에서 내가 쓴 실데이터 회귀 테스트 3건이었다:

| 테스트 | 경로 |
|---|---|
| `test_v65…::test_real_data_skips_known_holidays` | `pr.compute_pick_reliability(str(DATA))` |
| `test_v69…::test_report_carries_its_own_caveat` | `CD.measure(str(DATA))` → `_panel` → `_build_hl_union` |
| `test_v69…::TestRealMeasurement::rep` | 같음 |

`pick_reliability._build_hl_union(data_dir)`는 **설계상** 합집합을
`<data_dir>/ohlcv_union_hl.parquet`에 캐싱한다. 프로덕션에서는 옳다.
테스트가 진짜 `data/`를 넘겼기 때문에 캐시가 저장소에 떨어졌다.

### 처방

1. `tests/conftest.py::build_data_mirror` — 실데이터를 **심링크로 미러링**한
   디렉터리. 읽기는 그대로 통과하고 새 산출물은 tmp에 떨어진다.
   픽스처가 아니라 평범한 함수인 것은 의도다 — `CD.measure`가 14초라
   클래스 스코프로 한 번만 돌려야 하는 곳이 있고, 세션 공유 미러를 하나 두면
   A가 쓴 캐시를 B가 읽어 순서 의존이 생긴다.
2. 테스트 하나가 끝날 때마다 `data/`의 (이름, mtime, 크기) 서명을 비교해
   **더럽힌 테스트를 그 자리에서 지목**한다. 오버헤드 14초/6분(4%).
   끄려면 `SWINGPICKER_SKIP_DATA_GUARD=1`.

크기만 보는 가드로는 이번 사고(내용 동일·바이트 재작성)를 놓친다 —
mtime을 함께 본다. 변이 검정으로 고정했다.

### 아직 안 고친 것 — `ml_engine`

`ml_engine`은 `data_dir` 파라미터 없이 경로를 **하드코딩**한다:

```python
FEATURE_CACHE_SCHEMA_PATH = "data/feature_cache_schema.json"   # ml_engine.py:101
```

cwd가 저장소면 그대로 덮는다. 미러 픽스처로는 막을 수 없다.
이 세션 앞부분에서 `feature_cache_schema.json`이 n_stocks 672→595로 덮였는데
그때는 트리거를 못 찾았다 — **메커니즘은 이제 확정**됐다(하드코딩 상대경로 + cwd).
프로덕션 모듈 변경이라 이번 PR 범위 밖으로 둔다. 다만 새 가드가 재발 시
범인을 지목한다.
